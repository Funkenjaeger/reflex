## reflex v1.2.0-rc.2

The touchscreen Update screen is back, and this time it updates both halves:
it flashes the controller through the field bootloader, checks that the new
firmware speaks the protocol the new UI expects, and only then installs the
UI. The register map is now generated from one schema, and the UI reads the
controller about 28 times a second instead of about 16. Firmware and UI must be
updated together.

### ⚠ Upgrade notes
- **Firmware and UI move together** (register protocol 10, up from 9).
- **Installing this from rc.1 is done by hand**, because rc.1 has no Update
  screen: check out the tag, sync the UI environment, and flash
  `reflex-app-1.2.0-rc.2.bin` with `modbus-flash.py`, as in the guide's
  *Installing on a Pi → Updating later → From the command line*. From rc.2
  onward, Setup → Update does it.
- **The Update screen needs** the field bootloader on the controller (see
  rc.1) and a git checkout of this repository. It fetches over HTTPS, so the
  Pi needs no GitHub key.

### What's new
- **In-app update, firmware and UI together** (Setup → Update). The UI half is
  installed only once the flashed firmware reports the protocol the new UI
  expects. If it reports anything else, the previous firmware is put back and
  confirmed running, and the UI is not touched. **Offer pre-releases
  (experimental)** adds release candidates to the list.
- **The controller enters its bootloader by a jump, not a reset.** BOOT0 is not
  connected on this controller board, so a reset could land it in the chip's
  own ROM bootloader, which only an ST-Link can recover. On the bench that
  happened 3 times in 7; by jump it happened 0 times in 30.
- **Generated register map** (protocol 10): one schema for the firmware and
  the UI, checked by the compiler. Each poll of the controller now takes two
  requests instead of three, which is what brings it back up to about 28 a
  second.
- **New boards:** `fw/scripts/provision.sh` installs the bootloader and the
  application in one step, and `flash.sh` refuses to overwrite the bootloader.

### Fixes
- **Cut** is offered only while **Sync Enable** is on (*"Turn Sync Enable on,
  then Cut"*). Before, a Cut pressed with sync off released the hold, and the
  next Sync Enable press moved the carriage.
- After turning **Sync Enable** off mid-cut, the action button comes back.
  It used to stay blank until the UI was restarted.
- Release firmware now reports the commit it was tagged at. rc.1's reported
  the commit before, marked `-dirty`.
- The flight recorder notes the instant each stop fired.

### Known limitation
- **The first start of new firmware can take about 30 s** (one watchdog period)
  after an in-app update, and this release's updater waits only 15 s. It can
  then report that flashing the controller failed, and leave the UI half
  uninstalled, for an update that did complete. Fixed in rc.3.

### Verified
Protocol 10 on the development lathe on 2026-09-07: 13 stops with 0 failed
reads across 22,426 ticks and every take-up verdict correct. The jump into the
bootloader on 2026-09-12: 30 of 30 entries with no ROM landings, then a flash
and a revert through it. The first touchscreen update on 2026-09-13 hit the
limitation above: the firmware update had completed, and a second attempt with
a longer wait finished the UI half. UI and system CI green on the promoted
commit. The firmware is byte-identical to a commit whose firmware CI was green.
