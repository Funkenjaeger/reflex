## reflex v1.2.0-rc.3

Fixes the stall after an in-app update. The first start of freshly flashed
firmware could hang for one watchdog period (about 30 s), and rc.2's updater
gave up before it came back. Both jumps, into and out of the bootloader, now
clear the flash caches, and the updater waits past a watchdog period. Same
register protocol as rc.2 (10).

### ⚠ Upgrade notes
- **The fix has two halves.** The application half installs from the
  touchscreen with this release. The bootloader half lives in a protected
  flash sector that only a programmer (SWD) can write: the `reflex-bl` asset
  here carries it. The development lathe already has it.
- **Updating from rc.2 can still stall once**, because rc.2's firmware and
  rc.2's updater run that update. If the Update screen reports that flashing
  failed, the firmware may well have been written anyway.
- **`reflex-fw-<version>` is no longer published.** It was the legacy image
  for boards without the bootloader, and no such board remains. Flash
  `reflex-app-<version>.bin` over RS-485. `fw/scripts/flash.sh` still builds
  and programs the legacy layout locally, for recovery.

### Fixes
- **Both jumps reset the flash caches** (the processor's ART accelerator):
  the application's before it hands over to the bootloader, and the
  bootloader's before it starts what it has just written. Without that, the
  new firmware could run stale cached code from the old one, hang, and wait
  for the watchdog.
- **The updater waits up to 45 s** for the new firmware to answer, longer than
  one watchdog period, and says so when the answer comes late.

### Verified
On the development lathe on 2026-09-13: rc.2's first start stalled on both
attempts without the cache reset, and came up in under 13 s on both attempts
with it. With the bootloader half installed over SWD, the update to this
release from the touchscreen took 13 s with no stall, where rc.2's had taken
45 s an hour earlier. CI green on the promoted commit.
